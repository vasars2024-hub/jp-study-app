Agents caught five of the first six. Two agents also fabricated illustrative numbers **inside the
skills forbidding fabrication**, both caught by the mandatory read-back — which is why that rule
exists and why it is the highest-value line in `jp-dispatch`.

### The near-miss that matters most — `FINDINGS_CONSENT_NEARMISS.md`

A freshly-created scratch profile read `jp-telemetry-consent=yes` and `jp-telemetry-pinged=1` with
no user interaction and no consent screen on display — and `pinged` is written *only* after a
confirmed successful send. **Six independent checks corroborated it**: the profile was fresh, the
`--user-data-dir` had taken, exactly one Electron instance existed, the real profile was untouched,
no code path seeds `yes`, and no source file had moved.

**Two controlled retests refuted it.** An untouched fresh profile held `consent: null` / `pinged:
null` for 45 s with the gate still up; declining wrote `no` and never pinged. The consent flow is
**correct** and now sits in §0b. The original observation is recorded as an unreproduced anomaly and
nothing more.

The other errors produced wrong *numbers*. This one would have produced a **false accusation about
user privacy**, in the document written to decide whether the app is fit to publish. The rule it
buys:

> **Corroboration is not reproduction.** Verifying the circumstances of an observation does not
> verify the observation. For any finding that accuses the software of acting against the user,
> reproduction on a clean fixture is mandatory *before it is written down*.

Paired with the standing rule that an absence is a scope hypothesis, that covers both directions:
**do not report what you failed to find, and do not report what you found once.**
