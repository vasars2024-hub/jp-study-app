## 3. C1-3 — the schedule, and why it lives where it does

The user's direction was "use an anime schedule for recent anime / new
releases, and match that against nyaa.si". The schedule is the spine and
releases are matched **onto** it, never the reverse.

- **Pure matcher** `src/shared/animeSchedule.ts`. The episode number is a hard
  gate applied *before* title scoring, so a perfect title on the wrong episode
  can never win. Verdicts are `exact` / `review` / `none`, and `review` is its
  own state all the way to the UI — collapsing it into `exact` is the F3
  dishonesty this module exists to prevent.
- **Four distinct no-release reasons**: unreachable index, index returned
  nothing, releases exist but not this episode, nothing matched closely enough.
  "The index had nothing" and "the index was unreachable" are different facts.
- **Network** `src/main/scraper/animeSchedule.ts`. AniList `airingSchedules`
  for the spine, the existing Nyaa RSS reader for releases, sequential and
  paced at 1.2 s. Pacing is explicit because `scraperRequest` only applies the
  safety policy under a scrape *runtime* (`http.ts:580-581`), and a schedule
  read is not a scrape job — without it this fans out one unthrottled request
  per scheduled episode.

**A correction I made mid-build, caught by a gate rather than by me.** I wrote
my own `releaseCoversEpisode`. `architecture-audit.cjs` failed with a
`duplicate-export` against `src/shared/malDownload.ts:273`, which already had
one — and a better one: it accepts only the forms release groups actually use
(`- 07`, `E07`, `S01E07`, `[07]`, `_07_`, `07v2`) and `coveredByBatchRange`

deleted mine and reused both. The dispatch told me to check the existing

**Placement.** No new Scraper page: nav labels are typed against the foreign

### Why point 4 could not pass, and what I did instead

**Nothing loads the ggml models.** `whisperWorker.ts:6-8` uses Transformers.js
with `env.allowLocalModels = false` and fetches ONNX weights by HuggingFace id.
The repo already knows: `whisperModels.ts:3-4` says the ggml entries "are not
used by the worker yet", and `StoragePage.tsx:28-33` deliberately hides them
because listing them *was* the "downloads don't match the dropdown" confusion.

So I drove the path that does run, with synthesised Japanese speech (SAPI
*Microsoft Haruka Desktop*, 16 kHz mono, 3.71 s, peak 89 % FS) as ground truth,
and found **two defects**, both now in `docs/KNOWN_ISSUES.md`:

- **KI-7** — the *default* Japanese tier `onnx-community/kotoba-whisper-v2.0`
  is gated. HF answers **401** to an anonymous request, confirmed with an
  instrument outside the app. The preference key was confirmed **absent** first,
  so this is the default path, not a stale user choice. Japanese transcription
  fails on first use for every user who has not opened the dropdown.
- **KI-8** — with a reachable model, the **default WebGPU device** returns
  `て。` for audio the CPU path transcribes correctly as
  `こんにちは 今日はいい天気ですね`. Same audio, same tier, same code; device is
  the only variable. Reproduced twice. The q4 decoder at `whisperWorker.ts:76`
  is the mechanistic suspect.

> **A trap I walked into and had to climb out of.** My first two transcripts
> were `。。。。。…` and `て。`, and I nearly reported them as a model defect. Both
> were **my instrument**: I read the WAV with a hardcoded 44-byte header offset,
> but SAPI writes an 18-byte `fmt ` chunk, so the data starts at **46** — two
> bytes off byte-swaps every `int16` sample into noise. Only after parsing the
> chunk properly, and separately confirming the audio's RMS and the text's
> codepoints, was the WebGPU/CPU split real. This is `jp-dispatch` §9.5: ask
> whether the fixture can show the thing before believing what it shows.

**Renderer storage restored.** Both `jp-study-whisper-model` and
`jp-study-whisper-device` were originally **absent**; both were removed again
and re-read as `null`. Renderer storage has no restore point, so this was
